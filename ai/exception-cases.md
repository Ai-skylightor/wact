# AI 异常用例生成

测试用例集的"正常路径"通常容易覆盖，但**异常路径**——参数缺失、类型错误、边界越界、特殊字符——往往是漏测的高发地带。人工逐条设计异常用例耗时且易遗漏，AI 异常用例生成能基于现有正常用例，自动派生多种异常场景，作为人工设计的补充。

入口在**任务管理**模块。AI 生成的异常用例不直接入库，而是进入**审批工作流**，由人工批量通过或驳回，确保只有合理的异常用例进入回归集。

## 异常场景类型

AI 会基于正常用例，从以下维度派生异常场景：

| 异常类型 | 示例（基于"创建用户"接口） | 测试目的 |
|---------|------------------------|---------|
| **参数缺失** | 不传 `phone` 字段 | 验证必填校验 |
| **类型错误** | `age` 传字符串 `"abc"` | 验证类型校验 |
| **空值** | `name` 传空字符串 `""` | 验证空值处理 |
| **边界值** | `phone` 传 10 位、12 位 | 验证长度边界 |
| **超长字符串** | `name` 传 1000 字符 | 验证长度上限 |
| **特殊字符** | `name` 传 SQL 注入 `'; DROP TABLE--` | 验证安全过滤 |
| **非法枚举** | `gender` 传 `X`（非 M/F） | 验证枚举校验 |
| **格式错误** | `email` 传 `not-an-email` | 验证格式校验 |
| **数值越界** | `age` 传 `-1` 或 `200` | 验证范围校验 |
| **重复提交** | 同一 `phone` 连续提交两次 | 验证幂等性 |

::: tip 异常用例的价值
异常用例不是为了"找后端的茬"，而是验证**接口契约的健壮性**。一个能优雅拒绝非法输入的接口，远比一个"任何输入都返回 200"的接口可靠。AI 异常用例生成的核心价值是**覆盖人工容易遗漏的边界**。
:::

## 工作原理

```
读取一条正常用例
  ↓ 提取参数：name / type / value / required
AI 按异常模板派生多条异常用例
  ↓ 每条 = 一个参数的某种异常变种
返回 JSON 数组（含异常类型标签）
  ↓
进入审批队列，人工批量审核
  ↓ 通过后入库为正式异常用例
```

AI 在派生时会保留：

- **原用例的业务上下文**（接口、其他参数的合理值）
- **异常类型的标签**（便于后续按类型筛选）
- **预期结果的推断**（如"应返回 400 + 错误信息"）

## 触发生成

### 从正常用例派生

最常见的入口——在已有正常用例的基础上派生异常：

1. 进入接口测试的用例列表
2. 选中一条正常用例 → 点击 **[AI 生成异常用例]**
3. 选择要派生的异常类型（可多选，默认全选）
4. 提交后任务进入异步队列
5. 任务完成后到任务管理页审批

### 批量派生

针对一个接口或一个模块下的所有正常用例批量派生：

1. 在任务管理页点击 **[新建异常生成任务]**
2. 选择范围：单接口 / 模块 / 项目
3. 选择异常类型（默认全选 10 种）
4. 提交异步任务
5. 任务进度面板实时显示处理进度

::: warning 异常用例数量爆炸
一条正常用例 × 10 种异常类型 = 10 条异常用例；100 条正常用例就会派生出 1000 条异常用例。建议**分接口 / 分模块**触发，避免一次生成过多导致审批疲劳。
:::

## 异步任务

异常用例生成采用与 [参数生成](./param-generation.md) 相同的异步任务机制：

- **任务队列**：提交后立即返回任务 ID，不阻塞前端
- **串行执行**：为避免压垮 AI 模型，默认串行处理每条用例
- **进度可见**：任务管理页显示已处理 / 总数 / 失败数 / 进度条
- **失败重试**：单条失败可重试，不影响整体任务
- **断点续跑**：任务中断后可从断点继续，不必从头开始

任务详情页字段：

| 字段 | 说明 |
|------|------|
| 任务 ID | 唯一标识 |
| 任务类型 | 异常用例生成 |
| 范围 | 接口 / 模块 / 项目名称 |
| 总用例数 | 涉及的正常用例数量 |
| 已生成 | 已派生完毕的异常用例数 |
| 失败数 | AI 调用失败或解析失败的次数 |
| 状态 | 排队中 / 运行中 / 已完成 / 部分失败 |
| 耗时 | 任务总执行时间 |

## 审批工作流

任务完成后，所有 AI 生成的异常用例进入**待审批**状态，需人工确认才会正式入库。

### 审批视图

进入任务详情 → 切换到 **[待审批]** 标签页，可以看到所有生成的异常用例，按异常类型分组展示：

```yaml
# 示例：异常用例卡片展示
原用例: 创建用户（phone=13800138000, name=张三, age=25）
异常类型: 参数缺失
异常用例: 创建用户（不传 phone, name=张三, age=25）
预期结果: 应返回 400 + "phone 字段必填"
AI 推理依据: phone 是 required=true 的字段，缺失应被校验拦截
```

### 批量审批操作

| 操作 | 作用 |
|------|------|
| **批量通过** | 一次通过所有当前筛选条件下的异常用例 |
| **批量驳回** | 一次驳回当前筛选条件下的所有用例 |
| **按类型通过** | 通过某一种异常类型的所有用例（如"全部通过参数缺失类"） |
| **按类型驳回** | 驳回某一种异常类型的所有用例 |
| **单条通过 / 驳回** | 针对个别用例精细操作 |
| **单条编辑** | 在 AI 生成基础上调整参数值或预期结果 |

::: tip 推荐的审批节奏
异常用例数量往往较多，逐条审批效率低。推荐做法：**先按类型批量驳回明显不合理的类型**（如某些接口对 SQL 注入已有统一中间件防护，相关用例可直接驳回），**再对剩余类型批量通过**，最后对个别用例做单条微调。
:::

## 预期结果的 AI 推断

异常用例的关键不只是"传入异常参数"，还包括"**预期应该返回什么**"。AI 会基于接口契约推断预期结果：

| 异常类型 | AI 推断的预期结果 |
|---------|-----------------|
| 参数缺失 | 返回 400 + 字段名 + "必填" |
| 类型错误 | 返回 400 + 类型不匹配错误 |
| 越界值 | 返回 400 + 范围校验错误 |
| SQL 注入字符 | 返回 400 + 安全过滤触发，或返回 200 但值被转义 |
| 重复提交 | 返回 409 + "资源已存在" |

::: warning 预期结果需人工复核
AI 推断的预期结果基于"理想的后端实现"，但实际后端可能：① 没做该校验（应返回 400 但实际返回 200）；② 错误信息文案不同；③ 状态码不同（如用 422 而非 400）。审批时务必结合实际后端行为调整预期结果，避免把"后端的 bug"固化成"用例的预期"。
:::

## 与正常用例的关系

异常用例与正常用例共同构成完整的接口测试集：

```
接口测试集
  ├─ 正常用例（手写 + AI 参数生成）
  │   └─ 验证接口"做对了"
  └─ 异常用例（AI 异常生成 + 人工补充）
      └─ 验证接口"拒绝了错的"
```

两者互补：只有正常用例通过率高，不代表接口健壮（可能任何输入都返回 200）；只有异常用例通过率高，不代表接口可用（可能根本没法正确处理合法请求）。**两类用例都需要**。

## 典型场景

### 场景一：新接口上线前的健壮性测试

后端交付新接口后，除了正常功能验证，还需要做一轮异常输入测试：

1. 先用 [AI 参数生成](./param-generation.md) 准备正常用例并验证通过
2. 在通过的正常用例上派生异常用例
3. 审批入库
4. 执行异常用例集，查看后端对异常输入的处理
5. 发现"应返回 400 但实际返回 500"类问题，提交缺陷

### 场景二：回归集的异常覆盖补充

已有回归集主要覆盖正常路径，发版前想补充异常覆盖：

1. 在任务管理页新建批量异常生成任务
2. 选择目标模块的所有正常用例
3. 选择 5 种核心异常类型（参数缺失 / 类型错误 / 空值 / 越界 / 特殊字符）
4. 提交异步任务
5. 审批后加入回归集，纳入持续集成

### 场景三：安全测试前置

在安全扫描之前，先用 AI 生成一批注入类异常用例：

1. 针对核心接口生成异常用例
2. 在异常类型中只勾选"SQL 注入""XSS"等安全相关类型
3. 执行这些用例，观察后端响应
4. 提前发现注入漏洞，避免上线后被安全扫描暴露

## 常见问题

**Q：AI 生成的异常用例会不会太多导致回归集膨胀？**
A：会。建议按需生成——只对核心接口、关键字段生成异常用例，避免对所有接口所有字段无差别覆盖。审批时主动驳回价值不高的类型。

**Q：异常用例失败（返回非预期状态码）= 后端有 bug 吗？**
A：不一定。可能是后端有意设计（如统一异常处理返回 200 + error 字段）。需要结合接口文档与后端确认后再判断是 bug 还是设计。

**Q：可以基于历史缺陷生成异常用例吗？**
A：当前版本不直接支持，但可以在审批阶段人工补充"曾经出过问题的边界值"作为补充用例。
