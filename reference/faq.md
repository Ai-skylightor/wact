# 常见问题

本页收录用户在实际使用中遇到的高频问题。按问题类型分组，每条给出**原因分析**和**排查步骤**。如果你的问题在这里找不到答案，可以提供更详细信息后向我们反馈。

## 启动与连接

### Q1：平台打不开 / 浏览器一直转圈

**原因**：服务未启动、端口被占用、防火墙拦截。

**排查**：

1. 在服务器上确认进程：Windows 用任务管理器看 `python.exe` / `node.exe`；Linux 用 `ps aux | grep python`
2. 确认端口监听：`netstat -ano | findstr :12180`（Windows）或 `ss -tlnp | grep 12180`（Linux）
3. 检查防火墙是否放行端口
4. 看后端启动日志有无报错（特别是数据库连接）

### Q2：端口被占用，启动失败

**原因**：12180（或自定义端口）已被其他进程占用。

**排查**：

```bash
# Windows
netstat -ano | findstr :12180
tasklist | findstr <PID>

# Linux
ss -tlnp | grep 12180
lsof -i :12180
```

**解决**：结束占用进程，或修改平台配置文件换一个端口。

### Q3：数据库连接失败

**典型报错**：`Can't connect to MySQL server` / `password authentication failed`。

**排查**：

1. 数据库服务是否启动：`systemctl status mysql`（Linux）
2. 数据库地址、端口、用户名、密码是否和平台配置文件一致
3. 数据库是否给平台所在服务器授权了远程访问（MySQL 的 `host` 字段）
4. 防火墙是否放行数据库端口（默认 3306）
5. 用 `mysql -h <db-host> -u <user> -p` 在平台服务器上手动连一次验证

## 登录与鉴权

### Q4：登录失败，提示用户名或密码错误

**排查**：

1. 用户名密码是否正确（初始账号通常是 `admin / admin`，首次登录后必须改密码）
2. 密码是否含特殊字符被前端转义（尝试用简单的临时密码验证）
3. 数据库里用户表是否真有这个账号（管理员可查）
4. 大小写是否正确（部分数据库默认大小写敏感）

### Q5：登录成功但接口返回 401 / Token 过期

**原因**：JWT 已过期（默认 12 小时）。

**解决**：

1. 重新登录获取新 Token
2. 前端代码会自动续期，如果是手写脚本调用接口要处理 401 重试
3. 如果一登录就 401，检查服务器时间是否准确（JWT 依赖时间戳）

## Swagger 与数据导入

### Q6：Swagger 导入失败

**典型报错**：`Failed to fetch swagger doc` / `Invalid swagger format`。

**排查**：

1. **网络可达性**：在平台服务器上 `curl <swagger-url>` 验证能否拉到文档
2. **URL 正确性**：Spring Boot 通常是 `/v2/api-docs` 或 `/v3/api-docs`，确认路径
3. **格式合法性**：把 URL 内容下载下来，到 `https://editor.swagger.io` 验证 JSON / YAML 是否合法
4. **跨域 / 鉴权**：如果 Swagger 端点需要登录，先在浏览器登录后再拿 URL
5. **版本兼容**：平台主要支持 OpenAPI 2.0 / 3.0，更老的版本可能解析失败

### Q7：Swagger 解析后参数对不上

**原因**：接口定义有 `oneOf` / `anyOf` / 复杂嵌套，或参数用了 `$ref` 引用。

**解决**：手动在「接口参数总览」里修正；或在用例编辑页直接改参数 JSON。

## 用例执行

### Q8：测试用例全失败 / 全部连接超时

**最高频原因**：`baseUrl` 配置错误。

**典型错误写法**：

```
❌ htp:/192.168.0.112:8080        （http 拼写错）
❌ http//192.168.0.112:8080        （少了冒号）
❌ http://192.168.0.112:8080/      （末尾多斜杠）
❌ http://localhost:8080           （在服务器上跑时 localhost 指服务器自己）
```

**排查**：

1. 在「执行测试」页看实际请求 URL，确认拼接正确
2. 在平台服务器上 `curl <baseUrl>` 验证目标服务可达
3. 确认目标环境没有 IP 白名单限制
4. 切换到测试环境的正确地址

### Q9：单个用例执行失败

**排查**：

1. 点「调试执行」单独跑这个用例，看「执行详情」里的实际请求和响应
2. 检查请求方法、路径、参数格式、请求头
3. 看 `error` 字段的具体内容：超时 / 404 / 500 / SSL 错误
4. 用 Postman 或 curl 复现一遍，确认是用例配置问题还是被测接口本身的问题

### Q10：断言不通过但响应看起来正确

**常见原因**：断言写法不正确，混淆了 HTTP 状态码和响应体的 code 字段。

| 断言写法 | 含义 |
|---------|------|
| `status=200` | HTTP 状态码等于 200（检查的是 HTTP 层） |
| `code=200` | 响应体 JSON 的 `code` 字段等于 200（检查的是业务层，**不是 HTTP 状态码**） |
| `code=0` | 响应体 JSON 的 `code` 字段等于 0（很多系统用 0 表示业务成功） |
| `contains:success` | 响应体包含字符串 `success` |

**关键区别**：`status=` 检查 HTTP 状态码，`code=` 检查响应体里的 code 字段。两者是不同的层面。

::: tip 不填断言时的智能默认
如果用例没设断言（expectValue 为空），系统会智能判断：
1. 先检查 HTTP 状态码是否为 200
2. 如果响应体有 `code` 字段，再检查 code 是否为 0 或 200（业务成功标志）
3. 如果响应体没有 code 字段，只看 HTTP 200

所以不填断言时，`{"code":500,"msg":"失败"}`（HTTP 200 但业务失败）也会被判失败，不会因为 HTTP 200 就误判通过。
:::

**嵌套 code 支持**：如果响应体的 code 字段不在顶层（如 `{"data":{"code":200}}`），断言 `code=200` 会自动在 `data.code`、`result.code` 等常见嵌套位置查找。

## 变量与参数

### Q11：变量未解析，请求里原样出现 `${varName}`

**排查**（按顺序）：

1. 占位符语法是否正确：必须 `${varName}` 或 &#123;&#123;varName&#125;&#125;，单层 `{}` 不识别
2. 变量名拼写是否和全局参数 / 局部参数里定义一致（区分大小写）
3. 全局参数是否启用（被禁用的不注入）
4. 用例是否归属正确的项目和用户（参数按项目 + 用户过滤）
5. 前置用例是否成功执行（前置失败则其提取的变量不可用）
6. 路径参数里的 `${var}` 同样遵循这些规则

详见 [变量体系 - 常见错误写法对照表](../advanced/variables.md#常见错误写法对照表)。

### Q12：`${int(id)}` 类型转换不生效

**原因**：类型转换要求**整段值**就是这个表达式，不能混在长文本里。

```
✅ "id": "${int(id)}"
❌ "id": "ID_${int(id)}"      （混在文本里识别不了）
❌ "id": "${int (id)}"        （int 后多了空格）
```

### Q13：随机规则（如 `${phone()}`）不生成新值

**排查**：

1. 规则占位符是否带括号：`${phone()}` 而不是 `${phone}`
2. 函数名是否在内置规则列表里（详见 [数据工厂](../advanced/data-factory.md#内置随机规则)）
3. 后端日志是否有 `数据工厂引擎未启用` 警告（说明 Faker 依赖加载失败）

## AI 功能

### Q14：AI 功能不可用 / 一直转圈

**排查**：

1. 看页面右上角 AI 模型徽章颜色：绿色 = 在线，灰色 = 未连接
2. 到「AI 配置」页点「测试连接」，看是否能通
3. 默认模式（内置 Ollama）下，确认 Ollama 服务在跑：`curl http://localhost:11434/api/tags`
4. API 模式（DeepSeek / 智谱等）下，确认 API Key 有效、有余额
5. 模型名拼写正确（如 `qwen3:14b` 不是 `qwen:14b`）

### Q15：AI 生成的异常用例质量差

**改进**：

1. 切换到参数更大的模型（如 `qwen3:14b` 替代 `qwen3:7b`）
2. 给用例取有业务含义的名字（不要叫 `test1`、`test_api`）
3. 在用例描述里写清楚业务意图
4. 关联 Swagger 文档，让 AI 能读到完整参数约束
5. 通过任务中心的审批流程剔除垃圾用例，平台会反馈给 AI 学习

## Mock 与 UI 测试

### Q16：Mock 不生效，请求直接打到真实接口

**排查**：

1. 执行测试时是否勾选了「启用 Mock 数据」
2. Mock 规则的 URL 和方法是否与请求完全匹配
3. Mock 规则是否启用（被禁用的不生效）
4. Mock 规则是否归属当前项目

### Q17：UI 自动化执行没有截图 / 视频

**排查**：

1. UI 工作流是否在步骤里加了「截图」节点
2. 浏览器（Playwright）是否正常启动（看执行日志有无 Playwright 报错）
3. 截图保存目录是否有写权限
4. 磁盘是否已满

## CI 与定时任务

### Q18：CI 触发失败，返回 401

**原因**：`X-CI-Token` 不正确。

**排查**：

1. Token 是否拼写正确（无多余空格、换行）
2. Token 是否被重置过（联系管理员确认当前有效 Token）
3. Header 名是否正确：`X-CI-Token`（注意连字符、大小写）

### Q19：CI 触发成功但 totalSuites=0（没跑任何测试集）

**原因**：没有匹配到测试集。

**排查**：

1. 平台上是否有测试集勾选了「发版自动触发」
2. 测试集的 `baseUrl` 是否和请求体里的**完全一致**（区分大小写、末尾斜杠）
3. 测试集是否归属当前调用账号可见

### Q20：定时任务到点没执行

**排查**：

1. 任务是否处于「启用」状态
2. Cron 表达式是否正确（注意空格、星号位置）
3. 服务器时区是否和预期一致（`date` 命令验证）
4. 关联的测试套件是否还有用例
5. 后端调度器进程是否在运行（看日志有无 APScheduler 报错）

## 报告与导出

### Q21：测试报告打不开 / 加载慢

**排查**：

1. 报告文件是否还在（清理策略可能已删除）
2. 报告里响应体过大（接口返回超大 JSON）会拖慢渲染，可改用导出 Excel
3. 浏览器是否是最新版（旧版 Edge / IE 不支持）

### Q22：导出 Excel 失败

**排查**：

1. 后端是否安装了 `openpyxl` 依赖
2. 报告里是否有特殊字符导致编码问题
3. 导出数据量过大可能超时，分模块导出

## 性能与稳定性

### Q23：平台越来越慢

**可能原因**：

1. **报告累积过多**：到「测试报告」批量删除历史报告
2. **任务中心历史堆积**：清理已完成 / 失败任务
3. **数据库索引退化**：联系运维做一次数据库优化（VACUUM / 重建索引）
4. **服务器内存不足**：检查 `top` / 任务管理器，看是否需要扩容

### Q24：并发执行时部分用例超时

**原因**：被测服务并发能力有限，或平台与目标服务之间带宽不足。

**解决**：

1. **首选：切换为串行模式** —— 在「执行测试」页把执行模式改为串行（默认即串行），测试套件 / CI 回归测试集里同理。串行不会同时压目标系统，能根治超时
2. 适当拆分测试套件，降低单批并发量
3. 在「执行测试」时按模块分批跑
4. 增加单用例超时时间（在用例配置里设置）

## 其他

### Q25：如何在不同环境间切换测试

**方案**：

1. 在「全局参数」里创建不同环境的参数（如 `base_url` 的 test / prod 值）
2. 用例里用 `${base_url}` 引用
3. 执行时选择对应环境 → 注入不同参数值
4. 或在「执行测试」时直接配置 baseUrl（覆盖全局参数）

### Q26：如何批量迁移用例到另一个项目

**方案**：

1. 在原项目用「导出 Excel」把用例导出
2. 修改 Excel 里的项目 ID 字段
3. 在新项目用「导入 Excel」批量导入
4. 检查前置 / 后置依赖是否需要重新关联

## AI 失败诊断

### Q27：AI 诊断有时分类不准，为什么

AI 诊断采用「规则层 → 历史命中 → AI 兜底」三层机制。**特征明确的失败由规则秒判（如 5xx 一定是系统缺陷），不会错**。但如果失败现场特征模糊（比如接口返回 200 但字段含义变了），会进入 AI 兜底层，此时分类可能不够精确。

遇到不准的情况，可以：
- 看诊断给的「证据」和「根因」，即使是灰区，证据往往能启发思路
- 结合响应体人工确认（AI 诊断定位到的字段通常是对的）

### Q28：历史诊断案例怎么复用

每次 AI 诊断的结果会按"失败指纹"（HTTP 状态码 + 断言期望 + 响应结构 + 失败类型）存入知识库。下次遇到**相同指纹**的失败，直接复用历史诊断，不再调 AI。这意味着：

- 团队里第一次有人诊断了某个失败，后续所有人遇到同样的都会秒出结论
- 如果接口修复了，历史记录不会自动失效（它存的是当时的失败现场，仍可参考）
