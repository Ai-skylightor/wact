# 变量体系

变量是接口测试平台的"血管"——它把全局参数、局部参数、上游用例的响应字段、数据工厂的随机值，统一输送到下游用例的请求里。理解变量怎么写、怎么解析、怎么传递，是用好平台的前提。

本页是平台最核心的参考页，覆盖所有变量语法、类型转换、动态规则、提取与注入、前置后置用例、路径参数，以及用户最常踩的写法错误。

## 基础语法：两种格式

平台同时支持两种占位符格式：

| 格式 | 写法 | 出处 | 适用场景 |
|------|------|------|---------|
| **单花括号** | `${varName}` | 通用、贴近 Shell / Spring 习惯 | 默认推荐 |
| **双花括号** | &#123;&#123;varName&#125;&#125; | 贴近 Mustache / Vue 习惯 | 与前端模板共用同一份 JSON 时 |

两种格式**功能等价**，引擎会按同一套逻辑解析。你可以混用，但建议团队统一一种风格以提升可读性。

```json
{
  "Authorization": "Bearer ${token}",
  "userId": "{{userId}}"
}
```

::: tip 哪种格式更好？
- 如果你只做接口测试，**`${varName}`** 是大多数后端工程师最熟悉的写法
- 如果你的测试数据 JSON 同时被前端 Vue 模板使用，**&#123;&#123;varName&#125;&#125;** 能保持一致
- 实在拿不准就用 `${}`，这是平台的"默认风格"


## 类型转换

有时候上游传来的变量是字符串，但下游接口要求整数（例如 URL 路径参数 `/api/user/${id}`，业务要求 `id` 必须是数字而不是 `"123"`）。平台支持**整段值是类型转换表达式**的写法：

| 表达式 | 含义 | 等价格式 |
|--------|------|---------|
| `${int(var)}` | 把 `var` 转成整数 | &#123;&#123;int(var)&#125;&#125; |
| `${str(var)}` | 把 `var` 转成字符串（原样） | &#123;&#123;str(var)&#125;&#125; |

```json
{
  "id": "${int(userId)}",
  "code": "{{str(orderCode)}}"
}
```

::: warning 整段值必须是这个表达式
类型转换语法要求**整个字段值**就是转换表达式本身，不能嵌在长文本里。

✅ 可以：`"id": "${int(userId)}"`
❌ 不行：`"id": "ID_${int(userId)}"`（混在文本里，引擎识别不了）


## 动态生成规则

数据工厂内置的随机值规则，可以在用例里直接写。规则的标记是**带括号的占位符**，引擎通过"是否带括号"区分规则和普通变量，不会冲突。

| 规则 | 含义 | 示例输出 |
|------|------|---------|
| `${phone()}` | 随机中国大陆手机号 | `13812345678` |
| `${email()}` | 随机邮箱 | `test@domain.com` |
| `${name()}` | 随机中文姓名 | `张伟` |
| `${id_card()}` | 随机身份证号（18 位） | `110101199001011234` |
| `${random_string(N)}` | 长度 N 的随机字符串（字母 + 数字） | `aB3dE8fG`（N=8） |
| `${random(N)}` | N 位随机整数 | `42831`（N=5） |
| `${random(a-b)}` | 区间 [a, b] 内的随机整数（旧语法） | `42`（1-99） |
| `${enum(男,女,未知)}` | 从枚举集合中随机取一个 | `女` |
| `${datetime(-7d,+0d,%Y-%m-%d)}` | 区间内随机日期，按格式输出 | `2026-07-15` |
| `${timestamp()}` | 当前 Unix 时间戳（秒） | `1721460000` |

```json
{
  "phone": "${phone()}",
  "password": "Pwd_${random_string(8)}",
  "amount": "${random(100-9999)}"
}
```

规则的完整说明见 [数据工厂 - 内置随机规则](./data-factory.md#内置随机规则)。

## 变量提取（extractVariables）

变量提取让上游用例的响应字段成为下游用例可用的变量。在测试用例编辑页的「变量提取」区域配置，使用 **JSONPath** 语法定位字段。

```json
{
  "extractVariables": {
    "token": "$.data.token",
    "userId": "$.data.userInfo.id",
    "firstOrderId": "$.data.orders[0].orderId"
  }
}
```

### JSONPath 速查

| 表达式 | 含义 |
|--------|------|
| `$.foo` | 根对象的 `foo` 字段 |
| `$.data.bar` | 嵌套字段，路径用 `.` 分隔 |
| `$.list[0]` | 数组的第一个元素 |
| `$.list[-1]` | 数组的最后一个元素 |
| `$.list[*].id` | 数组里所有元素的 `id` 字段（返回列表） |
| `$..id` | 递归查找所有层级的 `id` 字段 |

::: tip JSONPath 提取失败怎么办？
如果响应 JSON 里找不到该路径，对应变量不会被设置，下游引用时会保留原占位符 `${varName}` 不替换。可以在响应详情里查看实际返回结构，对照修改路径。

也可以先在「调试执行」里跑一次，从响应面板复制正确的 JSONPath，避免肉眼数错层级。


## 前置 / 后置用例（preCaseIds / postCaseIds）

前置 / 后置用例是**变量跨用例传递**的机制。每个用例都可以配置：

- **`preCaseIds`**：执行本用例前先跑哪些用例（它们的提取变量对本用例可见）
- **`postCaseIds`**：执行本用例后再跑哪些用例（本用例的提取变量对它们可见）

### 工作流

```
[前置用例 A]  ──提取 token, userId──┐
                                     ▼
                              [当前用例 B]
                                     │
                                     ▼ 提取 orderId
                              [后置用例 C]
```

执行 B 时：

1. 引擎先按 `preCaseIds` 跑 A，提取 A 的响应字段（token、userId）注入变量池
2. 再跑 B 本身，B 的请求里可以用 `${token}` / `${userId}` 引用
3. B 执行完，按 B 的 `extractVariables` 提取 `orderId`
4. 引擎按 `postCaseIds` 跑 C，C 可以用 `${orderId}`

::: warning 前置 / 后置 ≠ 流程编排
- **前置 / 后置用例** 是**用例级别**的依赖关系，写在用例配置里，单独执行该用例时也会触发前置链路
- **流程编排** 是**模块 / 项目级别**的批量执行顺序，由画布拖拽配置

两者可以叠加：流程编排决定"先跑谁后跑谁"，前置后置决定"跑这个用例必须先跑哪个"。


## 路径参数（URL 里的变量）

请求路径里也支持变量占位符，用于动态拼接 URL：

```yaml
path: /api/user/${userId}
method: GET
```

或者强制类型转换：

```yaml
path: /api/order/{{int(orderId)}}
method: GET
```

执行时，引擎先做变量替换，再拼上 `baseUrl`。例如 `baseUrl=http://test.com`、`userId=42`，最终请求 `GET http://test.com/api/user/42`。

## 变量来源优先级

同一个变量名可能在多个来源都出现，平台按以下优先级取值（高优先级覆盖低优先级）：

```
局部参数（用例自身）  >  全局参数  >  前置用例提取  >  数据工厂规则
```

::: tip 局部参数是"覆盖"语义
局部参数默认用于**临时覆盖**全局参数（例如某个用例需要换一个不同的 Token 做权限测试）。如果同名，局部参数优先。


## 常见错误写法对照表

这是用户最常踩的坑。下表把错误写法和正确写法一一对照，遇到变量没被替换时优先排查。

| ❌ 错误写法 | ✅ 正确写法 | 错在哪 |
|-----------|-----------|--------|
| `$int({id})` | `${int(id)}` | 类型转换语法错位：`int()` 是表达式内部，`$` 和 `{}` 要包住整个表达式 |
| `{id05}` | `${id05}` | 单层 `{}` 不会被解析，必须 `${}` 或 &#123;&#123;&#125;&#125; |
| {id: ${int(id)&#125;&#125; | {"id": "${int(id)&#125;&#125;" | JSON 键也需要双引号，是 JSON 语法问题不是变量问题 |
| `${int (id)}` | `${int(id)}` | `int` 和 `(` 之间不能有空格，引擎按字面匹配 |
| `${ int(id) }` | `${int(id)}` | 表达式首尾不能有空格 |
| ${token&#125;&#125; | `${token}` | 多了一个 `}`，引号配对错乱 |
| &#123;&#123;token} | &#123;&#123;token&#125;&#125; | 双花括号必须配对 |
| `$token` | `${token}` | 单独的 `$` 不是占位符，必须 `${}` 完整包裹 |
| `${phone}` | `${phone()}` | 规则占位符要带括号，否则会被当成名为 `phone` 的普通变量 |
| `${random(8)` | `${random(8)}` | 缺少右括号，规则不闭合 |
| `${random 8}` | `${random(8)}` | 参数必须在括号内 |
| `${enum(A B C)}` | `${enum(A,B,C)}` | 枚举值用逗号分隔，不能用空格 |

::: details 为什么 `${int (id)}` 不行？
引擎对类型转换的识别是**字面字符串匹配**，而不是用复杂正则解析。例如匹配 `${int(id)}` 这个精确字符串后做 `int(value)` 转换。中间加空格会让字面字符串失配，引擎就把它当成普通变量名（找不到名为 `int (id)` 的变量），于是原样保留占位符不替换。

这种"字面匹配"设计的好处是**可预测、零歧义**——你看占位符是什么样，引擎就按什么样式匹配。代价是对空格、大小写敏感。


## 完整示例：登录 + 下单流程

下面用一个真实场景串起本页所有概念。

### 1. 登录用例（id: case_login）

```json
{
  "name": "登录",
  "method": "POST",
  "apiPath": "/api/auth/login",
  "parameters": {
    "username": "admin",
    "password": "123456"
  },
  "extractVariables": {
    "token": "$.data.token",
    "userId": "$.data.userId"
  }
}
```

### 2. 下单用例（id: case_create_order）

```json
{
  "name": "创建订单",
  "method": "POST",
  "apiPath": "/api/order/create",
  "headers": {
    "Authorization": "Bearer ${token}"
  },
  "parameters": {
    "userId": "${int(userId)}",
    "productId": "PROD_${random_string(6)}",
    "quantity": "${random(1-5)}",
    "remark": "auto-test"
  },
  "preCaseIds": ["case_login"],
  "extractVariables": {
    "orderId": "$.data.orderId"
  }
}
```

### 3. 查询订单用例（id: case_query_order）

```json
{
  "name": "查询订单详情",
  "method": "GET",
  "apiPath": "/api/order/{{int(orderId)}}",
  "headers": {
    "Authorization": "Bearer ${token}"
  },
  "preCaseIds": ["case_create_order"]
}
```

### 执行流程

1. 跑 `case_query_order`，引擎发现它依赖 `case_create_order`（preCaseIds）
2. 跑 `case_create_order`，发现它又依赖 `case_login`
3. 跑 `case_login`：登录成功 → 提取 `token`、`userId`
4. 跑 `case_create_order`：注入 `token`、`userId`，生成随机的 `productId` 和 `quantity`，下单成功 → 提取 `orderId`
5. 跑 `case_query_order`：URL 里的 &#123;&#123;int(orderId)&#125;&#125; 替换为整数 `orderId`，请求成功

整个流程跑下来，每次执行都是独立的、参数化的、可重复的。

## 调试技巧

::: tip 调试变量解析的最佳姿势
1. **单独执行**包含变量的用例，看「执行详情」里的"实际请求" — 替换后的最终值会显示在这里
2. 如果占位符原样出现在请求里，说明变量没被解析 — 按上面的"常见错误写法"表逐条排查
3. 全局 / 局部参数去「测试管理」对应页面查表，确认参数名拼写、是否启用
4. 前置用例的提取字段，看前置用例执行详情里的响应 JSON 是否真的有那个字段


::: warning 不要在生产环境用真实 Token 做变量
全局参数里的 `token` 容易被复用进多个用例，一旦泄漏影响面很大。建议：

- 测试环境用专门的测试账号 Token
- Token 通过前置用例（登录）实时获取，而不是硬编码在全局参数
- 数据工厂的 `${random_string(N)}` 用于业务字段而非凭证
