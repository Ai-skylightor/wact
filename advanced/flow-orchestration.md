# 接口流程编排

接口测试用例大多是**孤立**的——一个用例只调一个接口、断言一次返回。但真实业务往往是**多接口串联**：先登录拿 Token，再查询用户列表，拿到 userId 后创建订单，最后用订单号发起支付。这就是"接口流程"。

接口流程编排（Flow Orchestration）就是把多个用例按业务顺序串起来，并让前一个用例的输出（响应字段）自动注入到后一个用例的输入（请求参数）里。平台提供两种编排方式：**手动编排**和 **AI 自动编排**。

![接口流程编排](/screenshots/zh/flow_orch.png)

## 两种编排方式

### 手动编排

适用于你已经清楚业务顺序的场景。基本流程：

1. 在 **AI 功能 → 流程编排** 选中项目 / 模块
2. 从右侧用例列表中**拖拽**用例到中间的画布
3. 调整用例节点的先后顺序（拖拽即可换序）
4. 在每个节点上配置**变量提取**（从该用例响应里取出哪个字段）
5. 在下游用例的请求参数里用 `${字段名}` 引用上一步提取的变量
6. 点击「保存编排」并执行

### AI 自动编排（infer 推断）

适用于用例量大、人工理清依赖成本高的场景。

1. 选中项目 / 模块，点击「AI 自动编排」
2. 平台调用内置 AI（默认 Ollama，零配置可用），让 AI 分析这批用例的：
   - 请求路径与方法（推断语义，例如 `/login` 应该先执行）
   - 请求参数与响应字段（推断字段名匹配，例如响应里的 `token` 字段应注入到下游 `Authorization` 头）
   - Swagger 接口定义（如果已导入）
3. AI 输出建议的执行顺序 + 变量提取 / 注入方案
4. **置信度高**的方案自动应用；**置信度低**的方案进入待审状态，人工确认后再应用
5. 编排结果可随时手动微调

::: tip AI 编排会持续学习
平台记录每一次人工修正（拖拽换序、改字段映射），用作 AI 的 Few-Shot 样本，下一次类似用例集的推断准确率会更高。
:::

## AI 编排深度机制

### 静态分析器

AI 自动编排的第一步不是直接调 LLM，而是先用**静态分析器**（`static_analyzer.py`）做规则推断：

- **路径语义分析**：从接口路径推断业务含义（`/login` 先于 `/order`，`/create` 先于 `/delete`）
- **参数结构匹配**：上游响应字段名与下游请求参数名做相似度匹配（`token` -> `Authorization`）
- **命名规范推断**：用例名、模块名包含的语义线索（"登录"->"查询"->"下单"）
- **资源模式字典**：内置 28 类资源操作模式（CRUD/认证/支付/搜索等），匹配用例集属于哪种业务模式

静态分析产出的方案作为 LLM 的输入上下文，让 AI 不从零开始推断，而是基于规则预筛做精细化调整。

### 编排结果验证器

AI 输出的编排方案会经过**验证器**（`orchestration_validator.py`）校验后才应用：

- **循环依赖检测**：A->B->A 的环路会被拒绝
- **孤立节点检测**：没有任何连接的用例会被标记
- **变量完整性检测**：下游引用的 `${变量}` 是否都有上游提取来源

验证不通过的方案进入待审状态，而非直接丢弃。

### 用例模式库

平台维护一个**用例模式库**（`case_pattern_library` 表），沉淀常见的编排模式：

- 每次人工确认或修正编排后，系统会把"这组用例的执行顺序 + 变量映射"抽象成一个模式
- 下次遇到类似用例集时，先从模式库里匹配最接近的模式，作为 AI 推断的起点
- 模式库按项目隔离，不同项目的业务模式互不干扰

### 反馈学习闭环

```
AI 推断编排方案
    ↓
人工审阅：确认 / 修正（拖拽换序、改字段映射）
    ↓
修正记录写入 orchestration_feedback 表
    ↓
下次推断时，AI 读取历史反馈作为 Few-Shot 样本
    ↓
同时更新用例模式库
    ↓
推断准确率持续提升
```

这个闭环让 AI 编排不是"每次从零开始"，而是随着使用越来越懂你的业务。

## Jenkins 发版自动触发

编排结果不只服务于手动执行，还会**被 Jenkins 发版事件自动触发**：

```
Jenkins 发版完成
   ↓ POST /api/ci/trigger-all
平台执行所有开启「发版自动触发」的回归测试集
   ↓ 这些测试集会按编排好的依赖顺序执行用例
执行完毕同步返回结果汇总
   ↓
Jenkins 拿到 finalStatus 决定是否阻断流水线
```

详细对接方式见 [Jenkins 对接](../integration/jenkins.md)。

## 依赖检查

执行编排好的流程前，平台会做静态检查，避免低级错误：

- **路径参数是否齐全**：例如下游用例路径是 `/api/user/${userId}`，但上游没有任何用例提取过 `userId`，编排检查会标红
- **变量提取字段是否存在**：上游断言的 JSONPath 在响应模板里找不到对应字段
- **循环依赖**：A 依赖 B，B 又依赖 A，会拒绝执行

检查不通过时给出明确的错误定位，方便快速修正。

## 编排模式（Patterns）

以下是几种常见的编排模式，对照业务场景选择：

### 1. 线性流程（Linear）

最简单的串行链路。前一个用例的输出直接作为下一个的输入。

```
登录 → 查询用户ID → 创建订单 → 支付 → 验证订单状态
```

适用于：业务严格按时间顺序、每一步都依赖上一步的输出。

### 2. 扇出 / 扇入（Fan-out / Fan-in）

一个前置用例（如登录）的输出，被多个并行用例消费；最后由一个汇总用例收口。

```
           ┌→ 查询订单A
登录(Token) ┼→ 查询订单B   → 汇总断言全部订单状态
           └→ 查询订单C
```

适用于：需要并行验证多个独立资源、最后做整体断言。

### 3. 数据准备 / 业务测试 / 数据清理（Setup / Test / Teardown）

```
创建测试数据 → 跑业务用例 → 删除测试数据
```

适用于：避免脏数据污染生产 / 测试库，跑完即清。常配合数据工厂生成数据。

### 4. 条件分支（Conditional）

基于响应字段值决定走哪条分支。例如：

```
下单 → 判断 stock > 0 ?
        ├─ 是 → 支付流程
        └─ 否 → 库存预警用例
```

::: warning 条件分支当前是否支持
平台编排画布支持条件节点（if/else）的展示，具体可用性以平台版本为准。如果不支持，可在断言中用 `field:stock>0 or contains:out_of_stock` 这种"软分支"实现。
:::

## 变量在流程间传递

跨用例变量传递是流程编排的核心。完整机制见 [变量体系 - 前置 / 后置用例](./variables.md#前置-后置用例-precaseids-postcaseids)，这里给出最小可用例子。

### 步骤 1：登录用例提取 Token

在登录用例的「变量提取」里配置：

```json
{
  "extractVariables": {
    "token": "$.data.token",
    "userId": "$.data.userId"
  }
}
```

含义：从响应 JSON 用 JSONPath `$.data.token` 取出值，存入变量 `token`。

### 步骤 2：下游用例引用

下游用例（例如查询订单列表）的请求头或参数里：

```json
{
  "headers": {
    "Authorization": "Bearer ${token}"
  },
  "parameters": {
    "userId": "${userId}",
    "page": 1
  }
}
```

执行时，引擎先跑登录用例，提取出 `token` 和 `userId`，再把它们注入到下游用例发请求。

### 步骤 3：编排时连边

在流程画布里，把"登录"用例拖到"查询订单"之前，并用一根连线表示依赖关系。流程编排会自动按拓扑顺序执行，确保上游先跑。

## 操作步骤小结

完整的接口流程编排按这个清单走：

1. **创建项目 / 模块** — 用例必须挂在一个项目下才能编排
2. **创建用例** — 单独可执行的最小测试单元，详见 [测试用例管理](../api-testing/test-cases.md)
3. **进入流程编排** — AI 功能 → 流程编排 → 选项目
4. **选择编排方式** — 手动拖拽 或 AI 自动编排
5. **配置变量提取** — 在每个用例上设置要从响应里取哪些字段
6. **配置下游引用** — 用 `${变量名}` 在下游请求里引用
7. **依赖检查** — 确保所有变量都有来源、无循环依赖
8. **保存编排** — 编排结果持久化，下次执行 / CI 触发都按这套顺序来
9. **执行** — 单独执行 或 通过测试套件 / CI 触发

## 常见问题

::: warning AI 自动编排结果不可信怎么办？
AI 推断基于用例的语义信息和字段名相似度，遇到下面情况准确率会下降：

- 用例命名过于抽象（如 `test1`、`test_api`）→ 给用例取有业务含义的名字
- 接口路径无语义（如 `/api/v1/do`）→ 关联 Swagger 文档，AI 会读取接口描述
- 字段名重名（多个接口都有 `id` 字段）→ 用更具体的字段名，或在用例描述里写明含义

不确定时，置信度低的方案平台会让你手动确认，不要直接信任自动结果。
:::

::: tip 编排失败会不会影响用例本身？
不会。编排只是描述"用例怎么组织执行"，编排失败（例如 AI 推断出错、画布保存失败）不会改动用例本身的数据。可以随时重新编排。
:::
