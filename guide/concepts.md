# 核心概念

理解平台数据模型与几个跨模块的通用机制，是用好平台所有功能的前提。本篇把贯穿各个功能页面的核心概念集中讲清楚，后续章节不再重复。

![仪表盘](/screenshots/zh/dashboard.png)

## 层级关系：项目 → 模块 → 用例

平台所有测试资产按三层结构组织，自上而下依次是：

| 层级 | 作用 | 示例 |
|------|------|------|
| **项目（Project）** | 顶层业务边界，通常对应一条业务线或一个产品 | `电商前台`、`后台管理` |
| **模块（Module）** | 项目内的逻辑分组，对应一组相关接口或一个微服务 | `用户服务`、`订单服务` |
| **用例（Test Case）** | 单个接口的一次具体调用，含请求、断言、变量提取 | `登录-正常`、`下单-库存不足` |

这个层级会贯穿所有页面：左侧导航的项目树、Swagger 导入时的归属选择、执行测试时的模块筛选、报告里的分栏展示，都基于同一套结构。

::: tip 拆分原则
按服务边界拆模块，而不是按 CRUD 动作拆。`用户服务` 模块下放登录、注册、查询、修改、删除等用例，比拆成 `用户查询`、`用户写入` 两个模块更易维护。


## 参数体系：全局 vs 局部

平台把接口参数分成两类来源，它们在不同页面配置，但执行时会自动合并：

### 全局参数（Global Params）

- **作用范围**：所有用例自动注入
- **典型用途**：鉴权 Token、租户 ID、环境地址、公共版本号
- **配置位置**：左侧导航 → 测试管理 → 全局参数
- **环境隔离**：支持按 `test / prod / dev` 环境分类，执行时按选择注入不同值

### 局部参数（Local Params）

- **作用范围**：仅对某个具体用例生效
- **典型用途**：覆盖同名全局参数、临时调试、单个用例的特殊输入
- **配置位置**：测试用例编辑页内的局部参数区
- **优先级**：**局部参数 > 全局参数 > 用例参数**，同名时局部覆盖全局

详细配置见 [全局参数](../api-testing/global-params.md) 与 [局部参数](../api-testing/local-params.md)。

## 变量体系概述

平台支持三种变量引用语法，对应不同的求值场景：

| 语法 | 含义 | 示例 |
|------|------|------|
| `${var}` | 读取变量值，未定义时保留原样 | `${Authorization}` → `Bearer xxx` |
| &#123;&#123;var&#125;&#125; | 模板插值（部分场景支持） | https://$&#123;&#123;base_url&#125;&#125;/api/login |
| `${int(var)}` | 读取并对结果做类型转换 | `${int(pageSize)}` → `20` |

### 变量来源

执行一个用例时，平台会按以下顺序解析变量：

1. **用例局部参数**：优先级最高
2. **全局参数**：按当前选择的环境过滤
3. **上游用例提取的变量**：通过变量提取（extract）从响应中抓取，供下游用例使用

::: details 典型的变量链：登录后用 Token
1. 登录用例响应：`{"token": "abc123"}`
2. 在登录用例配置变量提取：`token` ← `$.token`
3. 后续业务用例请求头写：`Authorization: Bearer ${token}`
4. 执行时平台自动把 `abc123` 注入到后续请求


变量提取与依赖编排的完整用法见 [测试用例](../api-testing/test-cases.md) 与 [流程编排](../advanced/flow-orchestration.md)。

## Mock 服务

Mock 服务用于在真实接口未就绪时返回预定义数据，解决前后端并行开发与异常场景测试问题。

- **规则配置**：填写匹配 URL、HTTP 方法、响应状态码、响应体
- **匹配优先**：请求到来时优先匹配 Mock 规则，匹配不到才转发到真实接口
- **动态响应**：支持用 Python Faker 脚本生成随机数据
- **AI 生成**：描述需求让 AI 自动生成 Mock 规则
- **执行时启用**：执行测试勾选「启用 Mock」即可用 Mock 替代真实接口

详细用法见 [Mock 服务](../api-testing/mock.md)。

## 测试套件

测试套件把多个用例打包成一个可复用单元，用于批量执行与 CI/CD 集成。

- **典型场景**：把核心回归用例组成 `核心回归套件`，每天凌晨自动跑
- **引用方式**：在执行测试页或 CI/CD 定时任务中以套件为单位选择
- **与单个用例的关系**：一个用例可以同时属于多个套件，互不影响

详细用法见 [测试套件](../api-testing/test-suites.md)。

## 执行模型

理解平台的执行模型有助于排查失败用例：

1. **多模块执行（串行/并行）**：执行测试时选了多个模块，每个模块各自独立分栏展示结果。模块之间默认**串行**执行（保护被测系统），也可切并行
2. **模块内顺序**：同一模块内的用例按列表顺序执行，支持前置 / 后置依赖链
3. **变量作用域**：上游用例提取的变量在同一执行批次内对下游可见
4. **失败不中断**：默认情况下单条用例失败不会中断整批，所有用例都会跑完
5. **baseUrl 智能修正**：用例里写的是相对路径（`/api/login`），执行时拼接上你填的 baseUrl；如果用例里已经写了完整 URL，则智能保留不重复拼接
