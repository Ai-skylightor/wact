# AI Capabilities Overview

AI is not an "add-on" on this platform — it is a core capability **deeply integrated into the full testing lifecycle**. From API parameter generation, exception-case supplementation, and UI step orchestration, to page structure analysis and Mock data generation, AI delivers significant efficiency gains in every most time-consuming manual step.

This section starts with the full landscape of AI capabilities and how models are connected; subsequent sections drill into detailed usage for each scenario.

![AI Config Entry](/screenshots/en/ai_config.png)

## AI Scenarios Overview

The platform currently integrates AI deeply in these nine scenarios:

| Scenario | Problem Solved | Entry Point |
|----------|----------------|-------------|
| **Parameter Generation** | Intelligently generate test data from Swagger parameter definitions; no more hand-crafting data | Dashboard AI card / API details |
| **Exception Case Generation** | Auto-derive exception scenarios (missing parameter, wrong type, boundary value) from a happy-path case | Task Management |
| **Web Case Generation** | Requirement docs -> Yunxiao-format Web functional test cases, one-click Excel export | Portal - AI Case Generation |
| **UI Step Generation** | Natural-language description -> auto-generate Playwright UI operation steps | Flow Orchestration - AI Assistant |
| **Page Analysis** | AI opens the page, screenshots it, reads the DOM, and understands page structure and interactive elements | UI Flow Orchestration / Element Library |
| **Flow Orchestration** | AI infers step order, adds waits and assertions, and assembles a complete flow | Flow Orchestration - Smart Inference |
| **Mock Generation** | Generate Faker Mock scripts and sample cases from API definitions | API Testing - Mock Generation |
| **AI Auto-Testing** | Signal sources (docs/code/contracts) -> indexing -> code diff impact analysis -> AI-generated regression cases -> reflection loop self-correction | AI Auto-Testing |
| **Failure Attribution** | Rule-layer instant diagnosis + fingerprint cache reuse + LLM fallback, three-layer pipeline for root cause analysis | Test Report - AI Diagnosis |

::: tip AI Does Not "Do It All for You"
Content generated by AI requires **manual approval** before it is officially stored. The platform's design philosophy is "AI accelerates, humans gatekeep" — you get the efficiency of AI while retaining control over testing quality.
:::

## Supported Model Providers

Built on the LiteLLM unified abstraction layer, the platform supports 100+ providers. Out-of-the-box presets include:

| Provider | base_url | Auth Method | Typical Model |
|----------|----------|-------------|---------------|
| **Ollama (Local)** | `http://192.168.0.112:11434` | No key needed | `qwen3:14b` |
| **DeepSeek** | `https://api.deepseek.com/v1` | API Key | `deepseek-chat` |
| **Zhipu GLM** | `https://open.bigmodel.cn/api/paas/v4` | API Key | `glm-4-flash` |
| **Tongyi Qianwen** | `https://dashscope.aliyuncs.com/compatible-mode/v1` | API Key | `qwen-plus` |
| **Kimi (Moonshot)** | `https://api.moonshot.cn/v1` | API Key | `moonshot-v1-8k` |
| **Anthropic (Claude)** | `https://api.anthropic.com` | API Key | `claude-sonnet-4-20250514` |
| **OpenAI** | `https://api.openai.com/v1` | API Key | `gpt-4o-mini` |
| **Custom** | Any OpenAI-compatible endpoint | As needed | As needed |

The platform is built on **LiteLLM** rather than the raw openai SDK, primarily to natively support the Anthropic Messages format (Claude's official API uses `/v1/messages`, not OpenAI's `/v1/chat/completions`). Switching providers is just a model-string prefix change: `openai/gpt-4o-mini`, `anthropic/claude-sonnet-4-20250514`, `ollama/qwen3:14b`.

## Two Usage Modes

The front end exposes only two modes — pick one, **out of the box**:

### Default Mode (Built-in Ollama, Zero Configuration)

- **The default state after first install** — every AI feature works without any configuration
- Front-end appearance: `provider` is pre-set to `ollama`; Base URL / Model are shown grayed out with built-in values; API Key is hidden
- Click "Test Connection" and it works — every AI scenario is immediately available

::: warning Zero-impact Upgrade
After the system refactor, you will never see "AI is all broken after upgrade, I must configure something on the config page first". Default mode = current behavior, zero-impact switch.
:::

### API Mode (Connect to Cloud Models)

- Pick any of `deepseek` / `zhipu` / `tongyi` / `kimi` / `anthropic` / `openai` / `custom`; the preset Base URL + Model are auto-filled
- The user only needs to fill in an **API Key**; save to take effect
- Switching back to `ollama` returns to default mode; the cloud key is retained in the DB (not deleted) for easy switching back and forth

For detailed configuration steps see [AI Model Configuration](./model-config.md).

## User-Level Isolation: Independent Configuration Per Person

AI configuration is **isolated per user** — each account maintains its own provider / API Key / model preferences. This means:

- You can plug in your own DeepSeek API Key without affecting colleagues using the default Ollama
- API Keys are stored encrypted and visible only to you
- Switching accounts switches AI configuration; team collaboration is non-interfering

## Unified Architecture for AI Calls

All 9 AI call sites in the platform go through a unified abstraction layer; none of them call `requests.post` raw any more:

```
9 AI call sites → llm_client.chat(prompt) ──read DB user config──→ LiteLLM SDK
                                                                   ↓
                                                       The corresponding provider's API
```

Call sites cover: parameter generation, single-case generation, connection test, Mock script generation, Mock case generation, flow orchestration inference, smart inference, UI step generation, and more. All calls share the same timeout, retry, and response-parsing strategy.

::: details Why a Unified Abstraction Matters
Before unification, the 9 call sites each hardcoded their URL and model name — changing one meant changing all 9. After unification, model configuration is maintained in one place and switching providers takes effect in one click. This is also why the platform can support both local Ollama and cloud models — every provider walks the exact same code path.
:::
