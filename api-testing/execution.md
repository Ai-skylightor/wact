# 执行测试

**路径**：左侧导航 → 执行与结果 → 执行测试

执行测试是把用例跑起来的入口页。它支持按项目 / 模块 / 套件灵活选择用例，支持**串行 / 并行模式**切换（默认串行，保护被测系统不被打挂），支持 Mock 模式，还能对 baseUrl 做智能修正——让你在测试 / 预发 / 生产之间切换时几乎不需要改任何配置。

![执行测试](/screenshots/zh/execute.png)

## 页面能力一览

| 能力 | 说明 |
|------|------|
| 项目 / 模块选择 | 支持搜索、多选 |
| 执行模式 | 🆕 多模块执行可选**串行（默认）/ 并行** |
| 测试套件选择 | 直接选套件，套件内用例自动加载 |
| 基础 URL 配置 | 拼接到每个用例的请求路径前 |
| Mock 模式 | 启用后命中 Mock 规则的请求走 Mock |
| 请求超时 🆕 | 自定义每个接口的请求超时秒数（默认 20s） |
| 实时进度 | 进度条 + 每条用例的实时状态 |
| 多模块分栏 | 每个模块各自独立分栏展示结果 |

## 操作步骤

1. 选择**项目**
2. 选择**模块**（支持搜索、多选）
3. 选择**执行模式**（默认串行，详见下节）
4. 配置**基础 URL**（会拼接到每个用例的请求路径前）
5. 可选：勾选「启用 Mock 数据」
6. 点击「开始执行」
7. 实时查看进度条与每条用例的通过 / 失败状态
8. 执行完成后查看结果或进入 [测试报告](./reports.md)

## 多模块执行模式：串行 / 并行 🆕

选择多个模块时，可以选择模块之间的执行方式：

| 模式 | 行为 | 适合场景 |
|------|------|---------|
| 🐢 **串行（默认）** | 模块之间按顺序执行，一个跑完再跑下一个 | 完整回归、被测系统扛不住并发、需要稳定可控的执行 |
| 🐰 **并行** | 模块之间并发执行 | 被测系统抗得住压、追求最快出结果 |

::: warning 为什么默认串行？
并行执行会**同时**向被测系统发起大量请求，容易把目标系统打崩（数据库连接池耗尽、服务 OOM、限流触发等）。**默认串行**可以保护目标系统，避免「测着测着把系统测挂了」。只有当你确认被测系统能扛住并发压力时，才切换到并行。
:::

### 怎么选

- **日常回归 / 全量测试** → 用默认**串行**，稳字当头
- **冒烟测试，急着看结果，且环境够强** → 切**并行**
- **被测系统较弱（如本地开发环境、单机服务）** → 务必**串行**

无论串行还是并行，每个模块都会各自独立分栏展示进度与结果：

- **结果隔离**：某个模块大面积失败不影响其他模块继续跑
- **依赖清晰**：同模块内用例按列表顺序 + 依赖链执行，跨模块无依赖

::: tip 模块内 vs 跨模块
变量提取（如登录后提取 token）只在**同一模块内**对下游用例可见。如果要跨模块共享 token，建议把登录用例与业务用例放在同一模块，或者用 [全局参数](./global-params.md) 预先配置好 token。
:::

## Mock 模式

勾选「启用 Mock 数据」后，本批次执行的所有请求会优先匹配 [Mock 服务](./mock.md) 规则：

- 命中 Mock 规则 → 返回 Mock 数据
- 未命中 → 正常请求真实接口

这个机制支持**部分 Mock**：

| 用例 | 是否配 Mock | 实际行为 |
|------|------------|---------|
| 登录 | 否 | 走真实接口，拿到真 token |
| 查询订单 | 否 | 走真实接口 |
| 调用第三方支付 | 是（Mock 500） | 走 Mock，模拟支付失败 |
| 发邮件 | 是（Mock 200） | 走 Mock，不真发邮件 |

被测核心接口走真实，外部依赖走 Mock，互不干扰。

## baseUrl 智能修正

执行时填写的「基础 URL」会拼接到每个用例的请求路径前。但实际使用中，用例里的路径写法可能五花八门：

| 用例里的路径 | 填写 baseUrl | 实际请求 URL |
|-------------|-------------|------------|
| `/api/login` | `http://test.com` | `http://test.com/api/login` |
| `api/login`（无前导斜杠） | `http://test.com` | `http://test.com/api/login` |
| `http://prod.com/api/login`（完整 URL） | `http://test.com` | `http://prod.com/api/login`（保留原 URL） |

平台会智能处理：

- 用例里是相对路径 → 拼接 baseUrl
- 用例里已经是完整 URL → **保留原 URL，不重复拼接**

这样你可以在同一批次里混合「需要切环境的用例」和「固定地址的用例」，无需为切环境逐条改路径。

::: details 配合全局参数切环境
更优雅的做法是把 baseUrl 配在 [全局参数](./global-params.md) 里：用例路径写 `${base_url}/api/login`，执行时选不同环境的 `base_url` 即可整体切换。两种方式可混用。
:::

## 执行特性

| 特性 | 说明 |
|------|------|
| **依赖链支持** | 用例间的前置 / 后置依赖与变量提取在执行时生效 |
| **全局变量注入** | `${token}`、`${base_url}` 等自动解析 |
| **失败不中断** | 单条用例失败不中断整批，所有用例都跑完 |
| **实时进度** | 每条用例的执行状态实时刷新 |
| **失败详情** | 失败用例显示完整错误信息（状态码、响应体、断言失败原因） |
| **串行/并行可选** 🆕 | 多模块执行时可切换模式，默认串行保护被测系统 |
| **AI 失败诊断** 🆕 | 调试失败用例时一键 AI 归因，区分"配置错误"还是"系统/环境问题"，并给修复建议 |

## AI 失败诊断（自校正）🆕

调试执行失败后，结果区会出现「🔍 AI 诊断」按钮。点击后系统自动分析失败原因，告诉你**是配置错了还是系统/环境的问题**，并给出修复建议。

### 三层归因机制

诊断不是简单地把失败现场丢给大模型，而是经过三层流水线，**既准又省**：

| 层次 | 作用 | 说明 |
|------|------|------|
| **① 规则层** | 秒判，0 token | 特征明确的失败用确定性规则直接定性，不调 AI |
| **② 历史命中** | 复用，0 token | 相同失败现场（指纹相同）命中过就复用历史诊断 |
| **③ AI 兜底** | 全覆盖 | 只有规则和历史都判不了的灰区，才调用大模型 |

规则层覆盖的高频场景：

| 规则 | 触发特征 | 归因 |
|------|---------|------|
| 变量未解析（深度追溯） | URL / 参数里残留 `${xxx}` 占位符 | **按根因区分**（见下） |
| 鉴权失败 | HTTP 401/403 + 响应含 token/认证/登录 | 环境问题 |
| 服务端异常 | HTTP 5xx + 响应含堆栈/异常 | 系统缺陷 |
| 提取路径错 | JSONPath 在响应里找不到（如少包一层 `data`） | 配置错误 |

::: tip 变量未解析 ≠ 一定是配置错误
占位符 `${newid}` 没被替换，系统会**追溯这个变量的来源链**——该从哪个前置用例提取？那个用例执行成功了吗？响应里有没有对应字段？据此区分真实根因：

| 真实根因 | 判定 |
|---------|------|
| 变量名压根没配提取规则 | 配置错误 |
| 来源前置用例本身失败了（返回 5xx） | **系统缺陷**（前置用例失败才是根因） |
| 来源用例成功但响应结构变了（字段改名/移除） | **接口变更** |
| 提取路径写错（少包一层 data 等） | 配置错误 |
:::

### 五种归因分类

| 分类 | 含义 |
|------|------|
| **配置错误** | 用例本身配错了（URL/参数/断言/提取路径），改配置即可解决 |
| **系统缺陷** | 被测系统有 bug（5xx、抛异常），应提给后端开发 |
| **环境问题** | 网络/鉴权/部署类（超时、token 失效、网关错误） |
| **接口变更** | 被测接口改了（字段改名/结构变化），需更新用例适配 |
| **无法确定** | 证据不足，建议人工核对 |

### 历史案例复用

每次 AI 诊断的结果都会存入诊断知识库。下次遇到**相同失败现场**，系统直接复用历史诊断，无需再调 AI——既省 token，又把团队的排查经验沉淀下来。

::: tip 在哪用
AI 诊断在两处可用：
- **调试执行面板**：编辑用例 → 调试执行 → 失败时点「🔍 AI 诊断」
- **测试报告详情页**：报告列表 → 查看详情 → 每个失败用例行旁有「🔍 AI 诊断」按钮，逐个诊断
:::

## 常见问题

### 执行卡住不动

- 看是不是有依赖链死锁（A 依赖 B，B 依赖 A）
- 看是不是某条用例的接口响应极慢（网络 / 服务问题）
- 看是不是被测系统没起 / 地址不通（连接超时会逐条等满超时时间）
- 排查方式：先用「调试执行」单独跑可疑用例

::: tip 连接超时的处理
如果某条用例的目标服务无响应，平台会在**连接 5 秒 / 读取 20 秒**后判定失败并继续下一条，不会一直卡死。大批量执行中如果发现大量用例都卡在 20 秒，多半是被测系统本身没通，先检查服务状态和 baseUrl。
:::

### baseUrl 拼接错了

- 检查 baseUrl 是否带尾斜杠（建议不带，如 `http://test.com` 而非 `http://test.com/`）
- 检查用例路径是否带前导斜杠（`/api/login` 与 `api/login` 都可以，平台会智能处理）
- 如果用例路径是完整 URL，确认这是你想要的（不会被 baseUrl 覆盖）

### Mock 没有生效

- 确认勾选了「启用 Mock 数据」
- 确认 [Mock 服务](./mock.md) 中对应规则处于启用状态
- 确认 URL 与方法完全匹配

### 跨模块拿不到上游变量

变量提取只在同一模块内有效。需要跨模块共享数据时：

- 把相关用例放到同一模块
- 或用全局参数预先配置
