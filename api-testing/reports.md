# 测试报告

**路径**：左侧导航 → 执行与结果 → 测试报告

每次执行测试后，平台自动生成一份完整的测试报告并入库。报告页是查看执行结果、定位失败原因、对外汇报质量的统一出口。报告支持 HTML 在线查看、Markdown 下载、Excel 导出三种形态，覆盖从本地排查到团队汇报的全部场景。

![测试报告](/screenshots/zh/reports.png)

## 报告列表

报告页顶部是一张按时间倒序的报告列表：

| 列 | 含义 |
|----|------|
| 报告时间 | 执行开始时间 |
| 项目 / 模块 | 本次执行涉及的范围 |
| 用例总数 | 参与执行的用例数量 |
| 通过 / 失败 | 通过与失败的用例数 |
| 通过率 | 通过用例 / 总用例 |
| 耗时 | 从执行开始到结束的总时长 |
| 执行人 | 触发本次执行的用户（CI 触发则显示 CI） |
| 操作 | 查看详情 / 导出 Excel / 下载 MD / 删除 |

列表支持按项目、时间范围、状态筛选。

## 报告内容

点击「查看详情」进入 HTML 报告页，内容包含：

### 1. 报告概览

顶部展示本次执行的汇总信息：通过率、总用例数、通过 / 失败 / 错误数、总耗时、执行环境（baseUrl、是否启用 Mock）。

### 2. 模块分栏

按模块分栏展示结果，每个模块独立显示通过率与失败用例数。多模块执行时（无论串行还是并行），这里能直观看到哪个模块健康、哪个模块有问题。

### 3. 懒加载（大批量报告秒开）🆕

当一次执行涉及大量模块（如几十上百个模块、几百上千条用例）时，报告如果一次性渲染所有内容会导致浏览器卡死。平台对 HTML 报告做了**懒加载优化**：

| 层级 | 默认状态 | 怎么看详情 |
|------|---------|-----------|
| 模块 | **折叠**，只显示标题 + 通过/失败数 | 点击模块标题 ▶ 展开 |
| 用例列表 | 展开模块后才加载 | 随模块一起渲染 |
| 用例详情（请求/响应） | **折叠** | 点击用例标题才加载详情 |

这样设计的出发点：

- **首屏只渲染摘要 + 模块标题**（几 KB），浏览器秒开
- 用例数据以 JSON 形式嵌入页面，点击时才按需生成 DOM
- 实测 **106 个模块、518 条用例**的报告（1.3MB）可以秒开，不再卡死
- 配合响应体 5KB 截断（见下），单条用例的详情也保持轻量

::: tip 不用担心看不到完整数据
懒加载只是「延迟渲染」，数据都还在。需要看哪个模块、哪条用例，点开即可，详情和以前完全一样。
:::

### 4. 用例级详情

每条用例可展开查看：

| 信息 | 说明 |
|------|------|
| 用例名称 | 测试目的 |
| 请求方法 + URL | 实际发出的请求 |
| 请求头 | 含注入的全局 / 局部参数 |
| 请求体 | 实际发送的参数（`${...}` 已解析） |
| 响应状态码 | HTTP / WebSocket 状态 |
| 响应体 | 完整响应内容 |
| 响应时间 | 单条用例的耗时（毫秒） |
| 断言结果 | 每条断言的通过 / 失败与实际值 |
| 错误信息 | 失败时的详细原因 |

::: tip 失败排查三步法
1. 看断言结果：哪条断言失败、期望值与实际值的差异
2. 看请求体：`${...}` 是否被正确解析、参数是否齐全
3. 看响应体：接口返回了什么，是参数错了还是接口本身的问题
:::

## 三种报告格式

### HTML 报告（在线查看）

浏览器直接打开，带样式与图表，适合：

- 在平台上快速排查
- 分享链接给团队成员（需登录平台）
- 截图贴到缺陷单或汇报文档

### Markdown 报告（下载）

下载 `.md` 文件，适合：

- 嵌入到项目 Wiki / 文档站
- 提交到代码仓库做版本归档
- 在 Markdown 渲染器中离线查看

### Excel 导出

导出 `.xlsx` 表格，每行一条用例，包含用例名、方法、URL、状态、响应时间、失败原因等字段，适合：

- 与产品 / 业务对齐测试范围
- 离线做数据分析（如统计接口响应时间分布）
- 提交给没有平台账号的外部评审方

## 操作步骤

### 查看最新报告

1. 进入测试报告页
2. 列表第一行即最近一次执行
3. 点击「查看详情」

### 导出 Excel

1. 在报告列表找到目标报告
2. 点击「导出 Excel」
3. 浏览器下载 `.xlsx` 文件

### 下载 Markdown

1. 进入报告详情页
2. 点击「下载 Markdown」
3. 把 `.md` 文件嵌入到你的文档

### 批量删除历史报告

1. 勾选多条报告
2. 点击「批量删除」

::: warning 数据库膨胀
每次执行都会生成报告，长期累积会占用数据库空间。建议定期清理半年以上的历史报告，或仅保留有意义的版本节点（如每次发版的报告）。
:::

## 常见用法

### 场景 1：发版后回归汇报

发版完跑一次全量回归，导出 Excel，按通过率排序，把失败的用例贴到缺陷单。这是测试主管最常见的汇报方式。

### 场景 2：对比两次执行

打开两份报告（不同时间的同一套件执行），对比通过率与失败用例清单，判断本次发版是否引入新问题、是否修复了既有问题。

### 场景 3：CI 触发的报告

CI/CD 定时任务触发的执行也会生成报告，执行人字段显示为「CI」。通过报告列表筛选 CI 报告，可以追踪每次自动回归的结果。

## 常见问题

### 报告能保存多久

只要数据库不删，报告一直保留。空间紧张时手动清理历史报告。

### 响应体被截断

为防止大批量报告过大导致浏览器卡死，报告里的响应体会**自动截断到 5KB**。截断后错误信息、状态码、断言结果仍完整可读，只是超长响应体（如大列表、文件流）的前 5KB 之后部分不显示。

如果需要完整响应，建议：

- 在用例的请求头里限制返回字段（如分页参数），让响应本身变小
- 用变量提取只保留关键字段
- 在用例的断言里直接校验关键字段，而不是靠人工看完整响应体

### 失败用例显示「错误」而非「失败」

- **失败**：断言未通过（接口通了但返回内容不符合预期）
- **错误**：请求本身没成功（网络超时、连接拒绝、DNS 解析失败等）

错误通常是环境问题（服务没起、网络不通、baseUrl 错），失败才是业务逻辑或参数问题。

### 报告里的变量值是空的

`${...}` 解析失败会保留原样或为空。常见原因：

- 全局参数没配或被禁用
- 上游变量提取失败（前置用例没成功执行）
- 变量名拼写错误
